# ADR-0002：对局同步模型（事件流同步）

**状态**：已接受（模型层，2026-10-03）。协议细节（消息 schema 定稿、重连边界用例、匹配流程）归 08 号票。
**关联**：ADR-0001；Spec 实现决策（服务端权威、三 Seam）；设计 002 §5（seed 分配与可重放性）

## 背景

1v1 在线对战需要双方看到一致的对局状态（同一题面板、同一镜像题、一致结算）；反作弊要求客户端零权威；MatchEngine 已被设计为只发布对局事件流的 seam（Spec 测试决策）。

## 决策

**事件流同步：服务端权威跑 MatchEngine，客户端只做两件事。**

1. **提交**：玩家作答经 SubmissionPort 上行（服务端判题、结算，客户端不预判结果）。
2. **渲染**：客户端接收服务端推送的对局事件流（回合开始/面板就绪/提交判定/行动结算/HP 变化/对局结束），逐事件应用本地渲染。

配套规则：

- **回合计时权威在服务端**（ClockPort）；客户端以服务端时间戳校偏后渲染倒计时，提交窗口以服务端判定为准（迟到的提交判无效，不判迟到方赢）。
- **断线重连**：服务端推送"当前快照（含事件序号）+ 之后的事件流"；快照即引擎状态，不需要独立的序列化格式。
- **事件序号单调递增**，客户端发现断号即触发重连请求——顺序与完整性由序号保证，不靠 WebSocket 本身。
- **单机与在线同构**：MatchEngine 只在服务端存在（Go 唯一实现，ADR-0001）。热座（01 号票）与在线对战（08 号票）的差别仅在连接拓扑——热座是同一台机器上的两个客户端窗口接入同一场本地对局，在线是两个远程客户端；事件流一律经 WebSocket 下发，客户端渲染层完全共用。
- **审计与重放**：服务端持久化事件日志（含判题 verdict 与 seed 引用），与设计 002 的 matchSeed 确定性共同支撑整场对局的服务端重放。

## 后果

- **(+)** 作弊面最小：客户端无权威状态，改内存/改包只能影响自己的渲染。
- **(+)** 同步 bug 面最小：状态转移只有一处（服务端引擎），客户端是纯应用层。
- **(+)** 观感自然：事件流携带中间事件（行动结算、闪避、伤害数字），天然支撑动画与观战回放。
- **(−)** 事件 schema 成为硬契约（proto 管理），每加一种游戏机制都要扩事件类型——这是接受的成本，也是护栏。

## 备选方案（被否原因）

- **快照推帧**（每次结算推全量状态）：实现最简，但冗余大、无中间事件、观感突兀，且掩盖了引擎事件流这个现成边界。
- **双端引擎 + 输入广播（lockstep）**：客户端持有权威状态，违背服务端权威与反作弊底线，直接排除。
