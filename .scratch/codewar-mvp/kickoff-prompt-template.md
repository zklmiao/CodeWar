## 2. 工作流

**第 1 步｜实态核对（防凭票文空写）**：票文提到的每个代码位置/接口/测试逐一回仓库核实（存在性、行为、实际路径）；票文与代码漂移 → 以代码实态为准并在正式稿注记漂移，票文修改留待人确认。核对前置票交付与测试现状（测试文件清单、规模、最近回归结论）。

**第 2 步｜草稿**：正文覆盖——范围（逐条映射票面验收清单，不增不减 + "不做"禁令清单）；设计约束（数值/算法/阈值不定死，列为呈报门）；阶段计划（每阶段可验证完成标准 + 构建/生成门禁）；交付协议。

**第 3 步｜审查**：按第 3-4 节口径逐条审查草稿，发现分级 + 锚点 + 修正去向写入审查报告；对相关包做存量测试审计（抽 5 个关键断言读源码核口径 + `-count=1` 重跑防缓存假象）。

**第 4 步｜正式稿**：吸收全部审查修正；每条发现标注落点；含第 5-7 节要求的全部节。

## 3. 口径定义（写作与审查共用，防各人解释不一）

- **虚假 pass**：测试通过但未验证所声称的行为——形态含：只断言"不报错"、mock 断言 mock 的配置式互证、断言常量而非被测行为、依赖缓存/执行顺序、无证据的人工目检宣称。
- **过度测试**：测实现细节而非外部行为、断言 UI 像素/布局（jsdom 无布局）、分钟级真实墙钟用例、对票面明示人工验收项做脆弱自动化、为覆盖率而写的镜像用例。
- **呈报门**：spec 未定值的裁决点（数值/算法/阈值/互斥规则）——实现前呈报建议值 + 理由，人批复后作为集中定义的可调常量实现。
- **回归基线**：一组具体命令与预期结果（含不得并行的执行注意），任何"修正"提交必须附其全绿证据。
- **UNVERIFIED**：无法在本环境验证的项——必须引用钉住该行为的既有测试名，禁止无证据 PASS。

## 4. 测试要求（可判定条款）

1. **合理、无过度测试**：新增测试收在项目测试决策的 seam 上（本仓库 = MatchEngine 事件流 / Judge / QuestionFactory；客户端走 data-testid 与 store 状态机）；正式稿必含"测试边界"节——必测清单 + **明确不测清单**（超纲项点名）；按第 3 节"过度测试"定义逐条排除。
2. **不存在虚假 pass**：按第 3 节定义逐条排除；断言具体值；错误路径优先；行为修复先红后绿留证；正式稿含测试硬约束节。
3. **既有测试若发现过度测试/虚假 pass**：存量审计结论必须写入审查报告（无问题也要附证据，不允许默认无问题）；确有问题的 → 记录现象与锚点 → **呈报人批准** → 修正提交附回归基线全绿证据 → 收口；未经批准不得动任何既有测试。
4. **核对已交付产物**：对照前置票关票记录、验收报告、ADR 递延清单，产出**三栏结论：漏做 / 不做（明确排除）/ 递延归属**；逐项标处置——进本票、另开小票、禁止顺手修。

## 5. 开发要求（可判定条款）

1. **不过度设计**：正式稿含"不做"禁令清单（按票点名）；只定语义、不定死数值；能复用既有机制不建平行实现；架构决策需 ADR 时在正式稿标注。
2. **业务逻辑覆盖必要场景**：必要场景清单（正常路径 + 错误路径 + 竞态 + 边界），每场景配测试锚点；审查补齐草稿遗漏场景。
3. **符合开发 spec**：与 spec/ADR/既有票据裁决逐条对照并在正式稿留对照表；冲突记录呈报，不当场裁决、不当场修复。

## 6. 阻塞与裁决协议（遇事不停摆、不擅自决）

- **裁决类**（数值/算法/互斥规则/spec 未定项）→ 呈报门：建议值 + 理由，人批复后实施。
- **冲突类**（spec ↔ 票据 ↔ 代码）→ 记录进审查报告 → 呈报人，不当场裁决、不当场修复。
- **环境阻塞类**（docker 未起、测试库污染、工具缺失、服务不可达）→ 记录现象 → 能修则修并记录 → 不能修则该项标 UNVERIFIED 并引用钉住行为的测试名，继续其余工作。
- **信息不足** → 呈报具体问题，不臆测、不编造。
- **如实报告**：测试失败/偶发失败如实记录（含重跑结果），不掩盖、不挑好听的写。
